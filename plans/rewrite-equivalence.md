# Rewrite equivalence

Status: all three steps are done. `Proof.prove` encodes integer, bitwise and floating-point sequences in the SMT backend, refuses an instruction whose modes the definition does not render, and reports each instruction it relied on with the differential coverage behind it. AMDGPU arithmetic renders MODE's FP_ROUND fields beside its denormal fields, and the solver proves it for every rounding mode. A decoded instruction enters a proof as the form of its own operands (`AMDGPUForms`, `SASSForms`), with constant-bank reads on SASS and carries through VCC on AMDGPU. Loads and stores of global memory are admitted on both ISAs: memory is an input and an output of a sequence, and a proof compares the final memory and the accesses made. A guarded SASS instruction (`@P0 MOV R2, R3`) is admitted where its unguarded form is, as that form's steps under the guard.

## Goal

Decide whether two short straight-line sequences of SASS or AMDGPU instructions compute the same result on every input, for every lane, under a stated set of live-out registers and memory. A rewrite counts as correct only when this check passes. Differential testing comes first, because it is cheap, and it only rejects candidates.

## What already exists

- Rendered semantics: `core/.../semantics/render` turns each instruction's machine definition into terms (`Definition`, `Render`, `Backend`), with a Scala backend (`ScalaBackend`) that the executable-semantics work runs.
- Differential checking: the `semantics-check` lanes (`isa/semantics-check`) compare rendered semantics with the VMs on generated inputs.
- The VMs execute whole kernels, so a candidate can also run in context.

## Steps

### 1. Differential filter

- Run both sequences on generated register and memory states through the VMs, one instruction at a time, using the `Reference` harness of `semantics-check`. Rendered definitions exist only as build-generated code, and `semantics-check` already compares them with the VMs. The executor is a parameter, so a rendered one can replace it. Generate edge values per operand type: zero, signs, NaN, infinities, denormals, and extremes.
- Compare the live-out state. Any difference rejects the candidate with a counterexample.
- This step decides nothing positive: surviving candidates go on to step 2.

### 2. SMT backend

- Add a `Backend` that prints a definition as SMT-LIB over bit-vectors, with floating point in the SMT-LIB float theory where the solver supports it.
- Encode both sequences over shared symbolic inputs, and assert that some live-out differs. `unsat` proves equivalence over the encoded semantics. `sat` gives a counterexample, which becomes a regression input for step 1.
- Memory is an array of bytes by 64-bit address in the solver's array theory, one per space, little-endian, which both sequences start from and neither knows the contents of. An access of n bytes reaches the n addresses from its own, and two accesses may overlap, wholly or in part, unless their addresses are proved apart. The backend already encoded the machine's plain loads and stores this way, and the theory is exact for symbolic addresses where a variable per touched address would need every alias case spelt out.
- With memory live out, two sequences are equivalent when on every input they leave the same live-out registers, the same final memory at every address, and make the same loads and the same stores, each an address and a width. The last is a second array per space and direction that holds, at the address of each access, a bit per width. An access may fault by its address, width and direction alone (unmapped, read-only, or misaligned, which NVIDIA faults and the SASS VM with it), so sequences that make the same accesses fault on the same inputs: a rewrite adds no fault and removes none. What registers and memory hold at a fault is not compared.
- A decoded instruction's global accesses enter a proof as those plain loads and stores (`GlobalAccess`): AMDGPU `GlobalMemory.loadN` and `storeN`, which the `global_*` and `s_load_*` forms render to, and SASS `Memory.loadGlobal` and `storeGlobal` of `LDG` and `STG`. AMDGPU LDS joins them as a second space (`Space.Shared`, `LocalMemory.loadN` and `storeN` of the `ds_*` forms): its addresses are 32 bits wide and an access reaches the bytes from its own address, wrapping at 32 bits, so the allocation is an input of the window, `shared_size`, which both sequences share and a proof bounds by the most the reference allocates (`Reference.allocation`). A byte at or past it reads zero and drops writes, as the VM does, so no access faults on it; the solver picks the size, and a counterexample replays on a harness that allocates it (`Reference.allocate`). Every other access stays as its ISA renders it and is refused: SASS shared memory (`LDS`, `STS`), whose accesses fault outside the allocation and window, flat addresses, which an aperture routes, scratch and local memory, and with them barriers, async copies, textures, buffers and images. A definition that both loads and stores is an update in place, as every atomic is, and is refused too, `ds_add_u32` among them.
- Locations are the 32-bit register units and flags the live sets name. A wide operand, such as `v[0:1]`, `s[2:3]`, VCC in a wave64 or a SASS pair, joins the units it spans, so a span and the registers under it are one state. Integers of one width share a location whatever their sign.
- A SASS constant-bank read is an input the window does not write: a read of one array of the banks' bytes, indexed by bank and offset, which both sequences share and nothing stores to. Reads that overlap agree byte for byte.
- An AMDGPU proof is over one lane, the lane a shared input below 64: `wave.lane()` is that input and `wave.ballot(p)` holds `p` in the lane's bit and zero elsewhere, as a wave with that lane alone active writes it. This holds for the whole wave only while no lane's result depends on another lane's bit, so a sequence that reads whole a mask a lane wrote before it is refused (`LaneMasks`, `Equivalence.crossLane`).

### 3. Trust in the semantics

- A proof is only as good as the rendered semantics. Every instruction a proof uses must pass its `semantics-check` lane. A proof report names the instructions it relies on, and the differential coverage behind each.
- Floating-point modes (rounding, denormal flush, `.FTZ`, `.SAT`) are part of each definition. An instruction whose modes are not all rendered is rejected, not assumed.
- A guarded SASS instruction lowers to a copy of its guard and then its steps, each under that copy. `InstructionSemantics` keeps each step's predicate and `StepRenderer.definition` renders a step under one as a condition, the construct the machine path already used for a predicated store, so a guard is no wrapper around a finished definition and no list names what may take one. Where the guard fails, each register, predicate and flag the instruction writes keeps its value, so its definition reads what it writes, as `StaticRegisterUse` says; a load sits in the taken arm of the select and a store under the condition, so no access is made and nothing faults. The guard is read before the instruction writes, so `@P0 ISETP P0, ...` selects on the old `P0`.
- A decoded instruction is admitted by its own form, and by nothing else: its own operands must render to a definition through the explorer's path, `Rejection` must admit that definition (plain memory accesses, which global loads and stores become, constant-bank reads, and the lane's own bit of a lane mask), every parameter and result must bind a location or a literal, and the lane must hold a checked case of the form. For SASS that is a case of the mnemonic whose instance has operands of the same kinds, under a guard of the same sense where the instruction has one. For AMDGPU the generator must check the mnemonic on the target or on the checked target of its ISA (`AMDGPUGenerator.checked`, so gfx1036 takes gfx1030's), and a proof also needs a case it keeps of the encoded mnemonic there, which is looked up only when a proof asks: describing every instance of a mnemonic costs far more than admitting one instruction. Windows, moves, the differential executor and `Proof` take the same `Form`, and a proof report names the cases behind each instruction.

## Checks

As in `cost-model.md`. In addition, known-equivalent and known-different pairs (strength reductions, identities, and off-by-one rewrites) form a golden suite.

## Non-goals

- Whole-kernel equivalence, loops, and control flow beyond a straight-line window.
- Proving rendered semantics correct against hardware. The `semantics-check` lanes and conformance do that.

## Limits

- AMDGPU add, subtract, multiply and fused multiply-add round as MODE.FP_ROUND says: its low two bits for binary32 and the next two for binary16 and binary64. Other AMDGPU float instructions are refused because they keep a fixed nearest-even rounding the hardware may not: the mixed-precision and dot forms, V_DIV_FMAS, atomics, and the matrix units. Bitwuzla has no `fp.to_ieee_bv`, so a floating-point value's bits are tied to its term by an equality, and the payload of a NaN the rendered semantics leaves open is the solver's choice: that of binary16 and binary32 fused multiply-add with a NaN operand, whose result the host picks. An invalid operation gives each ISA's measured NaN whatever the host is: the AMDGPU's negative quiet NaN at every width (gfx1036), NVIDIA's canonical 0x7fff and 0x7fffffff at binary16 and binary32 and the negative quiet NaN at binary64 (sm_89). Both are committed as `DefaultNaNSuite` in `amdgpu-vm` and `nvidia`. Other hardware generations are unmeasured. The differential filter types AMDGPU registers as integers, so it samples no float edge values; a pair that only differs on one needs more runs than the default 64.
- The lane checks constant-bank forms in bank 3 alone, which the rendering binds to memory, so a form renders and executes with its operand moved there and a proof assumes that the number of a bank selects what is read and nothing else. A constant offset held in a register lowers to a memory load and is refused. A solver counterexample that rests on what a bank holds, or that lies in a lane other than the reference's lane 4, cannot be replayed on the VMs and is undecided.
- SASS coverage tells forms apart by operand kinds, not by modifiers, so a modifier combination the explorer does not instance rides on the cases of its operand kinds; its own definition is still rendered and checked for modes. The instances the lanes check also hold each pair of an opcode and a modifier value that the encoding accepts together, up to 64 rows for a form, so a combination of two modifiers has a case. `SASSModifierAudit` (`semanticsCheck/Test/runMain net.kurobako.gemstone.isa.check.SASSModifierAudit <out.tsv> [sm_89 ...]`) lists every mnemonic, modifier combination and operand kinds that the committed fixtures use or a case instances, as covered, riding on the cases of its kinds, or refused with the reason. Refused for want of a rendering or a case: writes of uniform registers (`UMOV`, `UIADD3`, `ULDC`), which render through `Warp.leader`; and forms that write one predicate of two beside their sources (`IADD3 R2, P0, R4, R5, RZ`), which the assembler reads two ways, so no instance spells them. An instance also writes out the predicates a form leaves at their defaults, so `LOP3.LUT P0, ...` and `LEA R2, P0, ...` have cases. AMDGPU coverage is per encoded mnemonic on the target, since the generator keeps one case per definition up to names and numbers and none per operand form.
- A guard is checked once for each mnemonic, operand kinds and sense (`@P`, `@!P`): on the first instance of those kinds that lowers under one, with the guard on a predicate the instance does not name, and with the predicate sampled both ways. A guard that is also an operand rides on that case. A guard on a uniform predicate (`@UP0`) has no case and is refused, and so is a guarded matrix product, whose elements the reference runs with no guard. Still refused under a guard: whatever lowers with a branch, which is `BRA`, `CALL`, `RET`, `BAR`, and any instruction whose own steps are predicated, since its guard then lowers to a branch over them; and whatever is refused without one, for the same reason. That a guarded load makes no access where its guard fails is compared between two sequences on the VM and proved of the definition; like every load, it is not compared between the definition and execution.
- A proof with memory is over one lane, and holds for the wave only where the kernel has no data race inside the window: no other lane, wave or thread stores a byte this lane loads or stores during it, and none loads a byte it stores. A window holds no barrier and no atomic, so such an access is a race in the source. Without this even two stores at different offsets of one base do not commute, since one lane's second address can be another's first. The rewrite makes the accesses the original makes, so it races with nothing the original does not.
- The rule on accesses is stricter than the values need: a load whose result is dead is not removed, and a store is not split or joined (a dword store is not proved equal to its two halves, which fault on other addresses where alignment faults). The differential filter compares the bytes loaded and stored, each byte as the load returned it, so a load that a store to its address moved across is rejected even where its result is overwritten; it does not compare the width of each access, since a VM may make an access in other pieces than its definition; where only the solver tells two sequences apart by a width, the result is undecided. A replay starts from the solver's memory: the query reads back the initial bytes at every address its accesses reach, per space, and the VMs hold them before the run (`Reference.seed`), so a pair that only a memory content tells apart is decided. A model whose accesses fault on both sequences is tried once more with every access aligned to its width, and only a replay that then differs counts.
- The SASS lane checks plain global loads and stores on a harness where every address is mapped and a misaligned access is outside the definition's domain, as execution faults it: the rendered definition carries no alignment requirement of its own. A global access that reaches the constant bank where the lane binds it reads the bank's bytes, and a store there is outside the domain. SASS shared, local and generic accesses have no checked case. An AMDGPU LDS load executes on a launch whose LDS starts holding the bytes the harness holds where it reads, so a replay and the filter see what an earlier store wrote. The 64-bit and 128-bit forms (`LDG.64`, `STG.128`) render one access per 32-bit element and one check that the whole access is aligned to its largest power-of-two divisor, as execution and the card do; the solver marks the check's width in the footprint beside the element widths, so a wide access is not equal to the accesses of its parts.
- The lanes compare a definition with execution on its results and on the bytes written, not on the bytes loaded: a definition describes one lane, and execution of a cross-lane instruction loads for the others (the gfx1201 transposing loads read whole elements for every lane of a group). Loads are compared between the two sequences of a check, both on the VM.

## Open decisions

- Solver: the project avoids new dependencies. Recommendation: print SMT-LIB text and run an external solver binary (Bitwuzla or Z3) found through the toolchain registry, with no JVM library dependency. The check is then unavailable where no solver is installed, and says so.
- Data races: a proof with memory assumes the kernel has none inside a window (see Limits). Recommendation: accept, as every compiler does; the alternative is to refuse every window in which a store precedes another access.
- Faults: nothing here says an access cannot fault, so a rewrite keeps every access. Recommendation: keep this until a source says which loads are safe to drop, such as a load from the kernel's own argument buffer.
- Floating point: proved in the SMT floating-point theory, with each definition's rounding mode, flush, saturation and NaN handling. Integer and bitwise rewrites came first.

# Rewrite search

Status: proposed, not started. It depends on `static-pipeline.md` for its cost and on `rewrite-equivalence.md` for correctness.

## Goal

Find cheaper equivalent instruction sequences for short windows of compiled SASS or AMDGPU code on a chosen target. Search comes first. Reinforcement learning comes later, and only if search shows rewrites worth finding that search alone finds too slowly.

## Why search before RL

- A learner optimises its reward, and the reward is a model. The static pipeline model is a set of bounds and estimates, some of them `Estimate`. A learner finds where the model undercharges, such as an unmeasured pipe or an estimated latency, and reports gains the hardware does not have.
- Search with an exact correctness check and hardware validation shows how large real gains are, and where the model is wrong, before training on it.
- Search needs the same parts RL needs: an action space, a correctness check, a cost, and a way to emit code. Building them for search is not wasted.

## Parts

- **Windows:** straight-line sequences inside a basic block (`static-pipeline.md` step 1), with live-in and live-out registers from `RegisterUse` and liveness.
- **Moves:** replace an opcode, swap operands, insert or delete an instruction, or change an immediate. Each must be legal for the target, which the generated instruction catalogues decide, as the explorer already does.
- **Correctness:** the differential filter rejects most candidates cheaply. The SMT check proves the survivors.
- **Cost:** the static pipeline model for the block containing the window, with cycles per iteration as the objective, under the occupancy the kernel already has. A rewrite that changes register count also changes occupancy, which the cost includes.
- **Emission:** the SASS and AMDGPU encoders, which round-trip in tests. After a rewrite, the SASS control words (stall counts, barriers, yield) and the AMDGPU `s_delay_alu` and `s_nop` must be regenerated. That is a scheduling problem of its own and the largest risk in this plan.

## Steps

### 1. Superoptimiser

- Windows: `Liveness` and `Windows` in `core/.../flow` give static live-in and live-out sets and the windows of up to eight instructions, and `AMDGPUWindows` keeps the instructions the equivalence checker admits by their own form (`AMDGPUForms`, see `rewrite-equivalence.md` step 3), carries through VCC and loads and stores of global memory among them. A window that holds a store has memory live out whatever registers it leaves live, so it is never deleted as dead; `s_waitcnt` has no rendering and ends a window, so compiled code seldom has a load and the first use of its result in one window. The live sets carry VCC, SCC, EXEC and M0 as well as registers; a window stops at an instruction that writes EXEC, and no write ends the live range of a vector register. AMDGPU is done on gfx906 fixtures and on a gfx1036 code object: admission asks the checked cases of the target's ISA (`AMDGPUGenerator.checked`), so gfx1036 takes gfx1030's.
- SASS: `RegisterUses.of` in `isa/nvidia` gives the slots and condition flags a lowered VMIR instruction reads and writes, and `StaticRegisterUse` in `isa/sass-vm` names them `R`, `UR`, `P` and `UP` per decoded instruction through `VMAssembler.source`, with a guard as a read and a guarded write also a read so it never ends a live range; `SASSWindows` admits each instruction by its own form (`SASSForms`), constant-bank reads and `LDG` and `STG` among them, tested on the sm_89 `divergentSm89` fixture: 23 windows of up to eight instructions, three of them through a load or the store, where admission by mnemonic gave 20. A guarded instruction is admitted where its unguarded form is (`rewrite-equivalence.md` step 3), so a window runs through predicated arithmetic, loads and stores, and ends at a guarded branch as at any branch. `divergentSm89` guards only its branches and keeps its 23 windows. The compiled division `divideSm89`, which corrects its quotient under guards, goes from 11 windows over 26 of its 34 instructions to 23 over 31.
- Moves: `AMDGPUMoves` proposes one-move candidates of a window (opcode replacement within an operand-signature class from the catalogue, source swap, delete, insert, immediate change) from a seeded random source; each candidate round-trips through the encoder and decoder, holds only instructions `AMDGPUForms` admits, reads only live-in or earlier-written registers, and writes no live-out register the window does not write. AMDGPU only, on any target whose ISA has checked cases.
- Memory in moves: one rule in `Moves` (`ordered`) serves both proposers. A window's loads and stores are kept as they are and in their order: no move changes, deletes, reorders or creates one, and the other moves work around them. Whether two accesses may change places is for the proof, which tells apart addresses that may alias. On AMDGPU a load is itself by its text, and no candidate reads a register a load of the window wrote, since the `s_waitcnt` that makes it readable is outside the window. On SASS a reader waits on a load through its own control word, so a candidate may read what a load wrote, and control-word regeneration (step 2) owes it the barrier.
- SASS moves: `SASSMoves` proposes the same five kinds on sm_89 windows, sharing the kinds, seeded choice and register-effect filter through `Moves`. Each candidate round-trips through the sass-asm encoder and decoder, holds only instructions `SASSWindows.admitted` accepts, and obeys the same read and live-out rules. Every kind keeps the guard of the instruction it changes or copies: an opcode, swap or immediate change stays under its source's guard, an insert copies its source guard and all, which the read rule admits only where the guard's predicate is live in or written earlier, and no kind adds a guard or takes one away. A guarded `LDG` or `STG` is kept as decoded like any other, guard included. Kept instructions keep their decoded encoding word and scheduling in the model; changed and inserted ones carry neither, and the canonical encoder writes control word 0x7e0 for every instruction. Emitted bytes therefore do not preserve the original control words, so candidates serve for costing and proving, not emission, until control words are regenerated. A SASS load or store is itself only as decoded, with its encoding word: the canonical encoder writes URZ into the descriptor field of the `memdesc` forms of `LDG` and `STG`, and the rendered text the round trip compares does not show that field. The moves therefore keep each one as decoded and create none, and an emitter must write a kept load or store from its decoded word, changing only the control bits it regenerates, never from the canonical encoding of its text.
- Stochastic search over windows of up to about eight instructions, in the style of STOKE: MCMC over moves, with a cost of correctness distance plus model cycles.
- Search: `RewriteSearch` in the semantics-check main sources walks one-move candidates of a window with a seeded Metropolis rule over a cost of changed live-out bits plus cycles per iteration; every distinct candidate that changes no live-out bit and costs fewer cycles goes to `Proof`, and only a proved one is reported with the weakest timing source behind its gain. A window that leaves none of its writes live out has nothing to preserve, so the search evaluates one candidate, the deletion of the whole window, and reports it with the reason `no write is live out`. The search samples the move set, so a window with no rewrite is coverage, not a proof. A candidate the cost refuses is not ranked; the report lists it under the reason.
- Cost: `AMDGPUBlockCost` has one path, the block analysis of the static pipeline view. For each candidate it writes the kernel's assembly with the window replaced, re-targets the branches that cross the window, assembles it and replaces the kernel in the code object, then reads the VM's own static view of that code object (control flow, register use with implicit state, pipe, planned cycles, offsets). The launch is one of two inputs to that view, and both end in the same `BlockAnalysis.of`, which gives the cycles per iteration and their weakest source. A stated launch is recorded with `StaticProfile.stream` as one wave issuing the window's loop or block once with every lane active; `HardwareValidationSuite` records its rows the same way. A recorded launch of the unmodified kernel is issued again over the rewritten one with `StaticProfile.replay` (see below).
  - Addresses come from the new layout, so a rewrite that moves a loop into or out of one fetch line is charged the redirect that layout gives. Code after the window also moves; each report line says by how many bytes, and the cost does not include what that does to later loops.
  - Occupancy comes from the kernel descriptor's register count, changed by the granules the rewrite adds or frees over the whole kernel, and from the launch: the one the caller states (workgroup lanes, shared bytes, placement), or the one recorded.
  - A block that waves run once, with more than one wave resident under round-robin arbitration, costs the steady state of waves that follow one another (`PipelineSimulator.simulate` runs `Stream.overlapped`, the block as a repeating stream, and reports its cycles, binding and pressure; the entries stay one pass). The earlier measure, the finish of the last of 16 lockstep waves, depended on the order the waves reached the pipe: with one pipe 85 percent busy, one more issue moved that finish by 0.03 to 7 percent in either direction, so a dead instruction could score cheaper. The mean and the median finish move the same way (clover_flux, dead insert at 0: 47.06 against 48.00 and 50.11 against 50.13), seeded wave orders change nothing (the waves are identical, so relabelling them gives identical costs), and the busiest-pipe bound ignores dependency stalls. The steady state equals that bound when a pipe saturates (clover_flux window 22..29: 44.00 at every insertion position, against 52.00 to 52.59) and what the dependency chains allow when none does. It is also what a kernel with more workgroups than resident waves does: a wave that ends is replaced, so the fill and drain of one batch (8 of 52 cycles there) is not paid per wave. One wave, a single active partition (gfx1036 oldest-first, where the youngest wave really finishes later) and loops are unchanged; the SASS cost reads the same simulator. The cost of a short block that runs once per wave in a launch too small to replace waves is therefore optimistic by that fill and drain.
  - Not costed, and reported with the reason instead of an estimate: a target with no probed model of its own (gfx906), under a stated launch a loop or block that holds a memory instruction (no recorded traffic) and a loop with more than one path (no recorded issue counts), a size-changing rewrite of a kernel with a program-counter-relative instruction other than a branch, and a region the analysis withholds.
  - Not modelled: control words a rewrite would need (`s_nop` hazards on gfx1036), so a rewrite that creates a hazard is undercharged.
  - On the gfx1036 fixture `ctl_f4_tail`, the loop of that `HardwareValidationSuite` row, the unmodified block costs the 29.0 cycles the static view gives the row (29.01 measured). `ctl_f4_dead` adds a dead `v_mov_b32` to the loop; the default configuration proves its deletion at 29.00 from 30.00 cycles, weakest source `estimate` (the planned issue cycles are LLVM's). In the compiled `square_plus_one`, ten of the fifteen windows sit in a loop or block that reaches memory and are reported as not costed under a stated launch; the other five give no proved rewrite at seed 1, budget 3.
  - Recorded launch: `AMDGPUBlockCost.Launch.Recorded` holds the `ProfileStream` the VM's `ProfileRecorder` gives for a launch of the unmodified kernel, the stream behind `BenchmarkRunner analyse` and the explorer. `AMDGPUBlockCost.record` makes one through the explorer's `ProgramRun`. A launch records the register use its static view gives, implicit state included, so the two views cost a loop alike. The cost issues that stream again over the rewritten kernel's static rows and analyses the result, so the unmodified block costs what the dynamic view reports for the launch, and occupancy and lane activity are the launch's.
    - The rule holds for a rewrite that leaves the window's live-out state as it was, which the proof establishes before a rewrite is reported. Every instruction outside the window then issues as recorded, for the same lanes and with the same accesses, at its new address. The walk ranks unproved candidates by this cost; none is reported.
    - Inside the window, which is straight-line and writes no lane mask, every pass issues each instruction once for the same lanes. The original and the replacement are aligned by their longest common run of equal instructions. A kept instruction takes its issues and accesses. A changed or inserted instruction that does not reach memory issues once a pass with no accesses. A deleted instruction issues nothing and its accesses go.
    - Refused, with the reason: a changed or inserted instruction that reaches memory (the launch has no addresses for it), or that writes the lane mask; a kept instruction that reaches memory after its address reads a register the rewrite may have changed (the value a store writes does not count), or after the rewrite deletes a memory instruction. A register counts as changed once a deleted, changed or inserted instruction writes it, or a kept one that read a changed value, and stays so to the end of the window. A region the launch did not issue is not costed, and a loop whose blocks the launch issued unevenly is withheld by the analysis, so a loop with more than one path is costed only when the launch took one of them every time.
    - `AMDGPUBlockCostSuite` checks the rule against launches of the rewritten kernel: a deleted, a changed and an inserted instruction in a loop that loads and stores each cost what the dynamic view of that launch reports. In that loop the default configuration proves the deletion of a dead `v_mov_b32` at 157.00 from 159.00 cycles, weakest source `estimate`.
    - With a launch of `square_plus_one` over 20 elements, all fifteen windows are costed; none gives a proved rewrite at seed 1, budget 3.
    - The rule counts the address registers of a kept memory instruction, which `RegisterUses` names beside its reads, so a rewrite that changes only the value a store writes is costed and one that changes its address is refused. A memory form with no address field names all its reads as its address, and is refused as before.
    - Not covered: a launch that calls into another program, since the recording keeps no control flow for it.
  - SASS: `RewriteSearch.sass` runs the same driver (`RewriteSearch` is generic over an `Isa`, with AMDGPU and SASS instances) on an sm_89 window: windows from `SASSWindows`, candidates from `SASSMoves`, the proof through `SASSForms` and `SASSReference`, and a cost from `SASSBlockCost`. It costs a stated launch (one warp, every lane active) or a recorded one.
    - A candidate is spliced into the function's `Program`, laid out again by `Assembler.relaid` (code moves, direct branch targets follow, and a branch whose distance to its target changed is encoded anew), encoded and decoded, so a changed or inserted instruction has its machine form and word like any other. `ControlWords` then regenerates the control words of every path of the function, the unmodified window included, so "before" is the cost of regenerated words and not of ptxas's own; the rewrite alone is what the two differ by.
    - The static view is `LoadedProgram.staticTiming` of the rewritten function: the pipe of the first lowered instruction of each decoded one that has a pipe, the `Schedule.Encoded` of its regenerated stall and write barrier, and whether any lowered instruction reaches memory other than the kernel's parameters. `StaticProfile.stream` and `BlockAnalysis` then give cycles per iteration and their weakest source, through the region code `AMDGPUBlockCost` shares (`BlockRegion`). sm_89 has no fetch-line term, so there is no layout term. Occupancy takes the kernel's registers per thread, changed by the highest `R` slot the rewrite adds or frees over the whole kernel, in units of 8.
    - Not costed, and reported with the reason: under a stated launch a region that holds an instruction reaching global, shared or local memory (no recorded traffic) and a loop with more than one path; under either launch a region whose instruction has a write barrier and no table latency ("variable latency ... has no table latency": `DSETP` has none; the register classes of `S2R` and `S2UR`, `LDG.E.CONSTANT`, `SHFL.DOWN`, `DMUL`, `DADD`, `MUFU.RCP64H`, the `F2I` at 0x2e0 of `bitPackKernel`, and the `BREV`, `FLO`, `FRND` and `POPC` forms that `SASSMoves` may put in place of a `MOV` were probed), a size-changing candidate before a `RET.REL.NODEC` (its encoding depends on its address and the assembler cannot encode it from text), and a kernel whose control words cannot be regenerated. Reported rewrites are text with cycles; none is emitted as a cubin.
    - Recorded launch: `LaunchRecording.record` has the VM launch the kernel (`ProgramRun`, `Language.SASS`) for `groups` workgroups of `lanes` lanes, with one value for each explicit parameter: a scalar's value, or the size in bytes of a zeroed buffer. A cubin does not say which eight-byte parameters are pointers, so each of those is a buffer, a `double` included. `SASSBlockCost.of` takes a recording whose graph holds the kernel at the offsets of its decoded instructions, and the launch's resources. The rule that decides where each recorded issue goes is `RecordedIssues`, shared with `AMDGPUBlockCost`: the SASS instance has no lane-mask unit to guard, reads whether an instruction reaches memory from its static timing row, and takes every read of a kept memory instruction as deciding its address, since the register use of a decoded instruction does not say which reads form one. `StaticProfile.replay` drops an issue of the kernel that has no address, such as the machine's own setup, which a recording of a cubin holds.
    - `SASSBlockCostSuite` runs the recorded launch on the tail loop of `sumloop` (`branches.sm_89.cubin`), a loop that loads: the unmodified window costs what the dynamic view of the launch gives for the regenerated kernel, and a deleted, a changed and an inserted instruction cost, with their shift, what the dynamic view gives for a launch of the rewritten, regenerated kernel. A rewrite whose changed register feeds a kept load, and an inserted load, are refused with the reason.
    - `SASSBlockCostSuite` and `RewriteSearchSASSSuite` run on `intchain` with its code replaced by a block no load or store reaches: its `IADD3 R4, R2, 0x2, RZ`, whose result nothing reads, is proved removable and costed 2.17 from 2.67 cycles (estimate), and also replaceable by an `IMAD` at 2.42, a gain the model gives a dead write that no hardware shows (seed 1, budget 64). On the committed sm_89 cubins most windows are skipped or not costed for the reasons above; the runner finds one rewrite, in `branches` kernel `collatz` (seed 1, budget 24, 32 lanes): the dead `IMAD.U32 R1, RZ, RZ, c[0][0x28]` of the first window, 2.42 from 2.67 cycles (estimate), 16 bytes shorter.
- Runner: `RewriteSearchRunner` in the same package takes `<code-object> <kernel> <target>` and optional `--seed`, `--budget`, `--temperature` and `--window` flags, with the launch as `--lanes` (default one wave, 32 for an sm target), `--shared` and `--placement`, or as `--record groups` with `--arguments arg,arg,...`, which has the VM launch that many workgroups of `--lanes` lanes and costs from the recording (one argument for each kernel parameter: `<type>:<value>` for a scalar, with `i8`, `i16`, `i32`, `i64`, `f32` or `f64`, and `buffer:<bytes>` for a pointer, optionally followed by `:fill=<type>:<value>` for a constant or `:ramp=<type>[:start[:step]]` for `start + index * step`, so `buffer:1048576:fill=f32:1.0,i32:64,f64:0.5` is a one MiB buffer of ones, an `int` and a `double`; the code object says which parameters are pointers where it can, namely every AMDGPU kernel argument and each SASS parameter whose `.nv.info` `KPARAM_INFO` word carries a memory space, which ptxas 13.3 sets for a PTX `.ptr` and nvcc 13.3 does not, so an eight-byte SASS parameter a cubin does not mark takes either, and a stated argument that contradicts a marked parameter is refused), and prints one line per window and one per proved rewrite with its cycles before and after, the weakest source behind them and the bytes the later code moves. A target named `sm_<n>` runs the SASS driver on a cubin, with `--record` launching it as above.
- Run on real kernels: 30 kernels of 26 HeCBench HIP programs and the `clover_flux` benchmark fixture, built for gfx1036, each launched as `--record 2 --lanes 128` over zeroed 1 MiB buffers, seed 1, budget 3, 900 s cap per kernel. Seven kernels did not launch (zeroed inputs give wild addresses; three read a module global the launch does not bind; one ran out of heap) and four hit the cap with partial output. The 23 that ran gave 2,715 windows, of which 881 were searched and 820 costed, with 45,635 candidates of which 26,527 changed a live-out bit. 37 rewrites were proved, all with weakest source `estimate`; budget 64 on the five kernels with proved rewrites gave 87. 34 of the 37 (84 of the 87) inserted one dead instruction that the cost scored cheaper (clover_flux 52.00 to 51.70). The fetch-line layout was not the cause: the regions are straight-line blocks. The simulator issues the block for 16 resident waves in lockstep through one FP64 pipe (clover_flux, 85 percent busy) or load-store pipe (`div_kernel`, 84 percent busy), and one extra issue changes which wave reaches the pipe when, which moved the block's end by 19 cycles of 3,328 (clover_flux) and 82 of 1,298 (`div_kernel`). The search holds every candidate to the cost of the instructions it shares with the original window, so adding instructions never lowers the cost; at budget 3 on the five kernels with proved rewrites, only the three deletions remain. With the steady-state block cost above, `AMDGPUBlockCostSuite` passes the dead insert at every position of the clover_flux window without the floor, and a scan that inserts `s_nop 0`, `s_cmp_ge_u32 s8, s14` and `v_mov_b32 v0, v0` at every position of every costed window of the five kernels (1,349 costed insertions) finds no block that scores cheaper (71 of 227 in clover_flux before). Three deletions look real: `s_cmp_lg_u32 s2, 0` after an `s_andn2_b32` and a dead `s_xor_b32` in `jacobi_step` (1.75 to 1.50, 1.50 to 1.25), and `s_cmp_lg_u32 s0, 0` in `bitPackKernel` (5.31 to 5.06). - Uneven regions (T186 at `86caff05`, T187 at `0ccfeb05`): a region whose recorded issue counts differ is no longer withheld. The distinct counts are `c1 > ... > cm` with `c1` the entry count; the cost is the sum over the streams that keep the instructions issued at least `c_i` times, weighted by `(c_i - c_{i+1}) / c1`, and the full stream supplies the timeline, binding, pressure and source. An even region keeps one stream and its old cost; a nested loop in the region or a count above the entry is withheld. Only the region holding the window is analysed (`BlockAnalysis.region`), so a window outside the uneven region no longer pays for it: on `jacobi_step` that was 7 s per candidate for `block@0x3e0`, and a candidate on `block@0x0` now costs its own region alone (2.9 s to 0.16 s). The uneven region's own streams settle slowly: `block@0x3e0`'s two prefix streams (23 and 28 instructions) repeat their simulator state only after 257,000 and 380,000 to 780,000 cycles, at about 7 us a cycle, because the state key covers every resident warp's register readiness. A settle that has not repeated its state within 1,200,000 cycles is refused with `the steady state did not settle within 1200000 cycles`; unbounded marks ran an 8 GB heap out on `jacobi_step`. The same typed launches as above, seed 1, budget 3, on sora-ci-3900x: `jacobi_step` 41 windows, 5 not executed, 0 withheld, 36 searched, 20 costed, 1 proved, 832 candidates, 3441 s (main `c9706a2b`: 41, 5, 9 withheld for uneven counts, 27, 12, 1, 641, 648 s); `bitPackKernel<int, unsigned>` 198 windows, 68 not executed, 93 withheld for an inner loop, 37 searched, 15 costed, 2 proved, 534 candidates, 437 s (main: the same counts with the 93 withheld for uneven counts, 449 s). No rewrite is newly proved: the nine `jacobi_step` windows the uneven cost unblocks prove nothing, and the two bitpacking `VABSDIFF.U32` to `IMAD.U32` rewrites (6.80 and 6.83 from 6.90, estimate) are the ones main already reports.

### 2. Control-word regeneration

- AMDGPU first, where LLVM's model gives the delays: recompute `s_delay_alu` and `s_nop` for a rewritten block, and test against LLVM's output on the same sequence.
- AMDGPU done for straight-line blocks: `ControlWords` regenerates `s_delay_alu` as `AMDGPUInsertDelayAlu` does, from delay types, wait classes and tied operands that codegen takes from LLVM's instruction records into `scheduling.json`, and `s_nop` for three `GCNHazardRecognizer` rules (`s_setreg`/`s_getreg` repeats, a VMEM read of a VALU-written SGPR, a VALU overwriting a wide store's data) on GFX9 and earlier (LLVM skips them on GFX10 and later), and `FPAtomicToDenormMode` on GFX10. `ControlWordsSuite` matches LLVM on all 81 compiled blocks (gfx906, gfx1036, gfx1100, gfx1150, gfx1200). Not covered: VOPD pairs, DPP and SDWA forms, and every other hazard rule (VALU trans use, `v_div_fmas`, readlane, LDS, MFMA).
- gfx1036 (GFX10, no-data-dependency model): `FPAtomicToDenormMode` applies and is ported. It runs before the early returns in `getHazardType` and `PreEmitNoopsCommon`. An atomic on floating-point data (`FPAtomic`, set from the data type; probed with f32 `global_atomic_fmin`) owes wait states to a following `S_DENORM_MODE`.
  - The owed wait states are three: `s_nop 2` with nothing between, `s_nop 1` after one SALU, `s_nop 0` after two. Three SALU, a VALU or a waitcnt close the window. Integer atomics and gfx1100 do not trigger it.
  - The GFX9-only rules stay off on gfx1036: the early returns skip DPP, DivFMas, GetReg, SetReg, the VMEM-SGPR and wide-store checks, RFE, ReadM0 and the MAI family (`FeatureMAIInsts`, GFX9 sets only). Other rules need features gfx1036 lacks: the SMRD VALU def needs Southern Islands, NSAtoVMEM needs `hasNSAtoVMEMBug` (gfx101x), WMMA coexecution needs GFX12.5, and soft clause needs XNACK support, which gfx1036 lacks.
  - The post-RA fixers in `fixHazards` each fail a feature test: the gfx101x set (VcmpxPermlane, VMEMtoScalarWrite, SMEMtoVectorWrite, VcmpxExecWAR, LdsBranchVmemWAR), GFX11 and later (partial forwarding, VALU trans use, VALU mask write, required export priority, LdsDirect), GFX12.5 (trans and WMMA coexecution), GFX90A (Shift64 high register), and the GFX12 gates. The WMMA fixer also needs WMMA opcodes, which gfx1036 lacks.
  - The rest was traced from the LLVM 23.1.0 source, not probed on gfx1036. Feature accessors are generated from TableGen, so their gfx1036 values come from the `AMDGPU.td` feature sets. The fixtures come from llc 23.1.5.
  - The one SDWA block on gfx1036 (`v_cvt_f32_i32_sdwa`) regenerates exactly, and no ported rule applies to it.
- SASS: on sm_89 a cubin whose every function has its control words regenerated computes on the card what ptxas's original computes (below), but SASS rewrites stay reported: a changed or inserted instruction cannot be emitted yet. The groundwork is `ControlWords` in `isa/sass-asm`, which regenerates stall, yield, barriers and wait mask along each path (blocks chained by fallthrough) of a whole function from `control-words.json`. `ControlWordHarvestRunner` harvests that table from ptxas output: the least stall distance per producer form and written register against consumer form and operand position, the forms that set a write or a read barrier, the least spacing between two forms, and the idle stall between adjacent forms. The one latency per producer of `NvidiaLatency` does not give ptxas's stalls: a result crossing between the integer and the multiply pipes takes 5 cycles against 4, and a predicate read as a guard 13.
  - Barriers: a form ptxas gives a write barrier sets one, and the first instruction to read or overwrite its result waits on it. This is the barrier a candidate that reads what a load wrote is owed (see "Memory in moves"). A path leaves through a transfer that waits on every pending barrier and issues once the path's results are older than their table row maximum, so a branch target assumes nothing pending; the rule holds only when every path of the function is regenerated.
  - Emission: `ControlWords.encode(word, scheduling)` lays the regenerated control bits over an instruction's decoded word and changes nothing else, which is how a kept load or store must be written. `RegeneratedCubin` in `isa/sass-vm` does this for every kernel of a cubin and every function it calls, and `RegeneratedCubinRunner` writes the result. The encoding has no form without the yield bit for stall 0 or a stall above 11, so those always yield. A changed or inserted instruction has a decoded word and form once the assembler has encoded it (the cost path above does this), but nothing emits the rewritten kernel yet. Reuse flags are cleared: ptxas never flags a register that is rewritten before its next read in the same position, and on the card a stale flag changed nothing (below).
  - Harvest: `sbt "semanticsCheck/runMain net.kurobako.gemstone.isa.check.ControlWordHarvestRunner 89 <ptxas build> isa/sass-asm/src/main/resources/net/kurobako/gemstone/isa/sass/control-words.json isa/sass-vm/src/test/resources/net/kurobako/gemstone/isa/sass/controlwords target/conformance/artifacts/cuda/sm_89"`, after the conformance build of the `cuda` `sm_89` artifact (HeCBench, miniapps and unified cases, CUDA 13.3 container). One program in five is held out by file name. Coverage of the 646 sources: 3,137 kernels harvested or held out; 1,928 kernels left out because the VM does not lower them unbound (1,844 need a module global bound, 80 call a symbol outside the cubin, 4 hold an `I2F` form with no lowering), and 750 compressed fatbin entries left out. The inputs are too large to commit; `ControlWordsSuite` checks the table against the 36 committed kernels of `controlwords`.
  - Measure on the 125 held-out programs (400,176 instructions, 8,613 paths), which the runner prints and no suite requires: the stall matches ptxas on 88.8 percent of instructions and is not below it on 98.0 percent; the wait mask matches on 90.9 percent. 84.3 percent of paths have no stall below ptxas and 86.4 percent no dependency shorter than ptxas left it, so neither the exact nor the safe bar holds for every block. Every regenerated schedule meets the table, which is the only check a rewritten window can have, as it has no ptxas original; hardware decides whether that is enough. The largest classes below ptxas are a wide multiply feeding a load (5 against 6), stores and loads of shared memory after a multiply, and the stall after a variable-latency producer, where ptxas adds a wait the barrier does not need.
  - Card (RTX 4060 Ti, driver 620.70.06, loaded through `cuModuleLoadData`): it does not interlock on a fixed-latency result. Cutting ptxas's stall of 5 between `IADD3` and `IMAD` (`intchain` #5) to 4, or its 4 between `FADD` and `FMUL` (`floatchain` #5) to 3, gives wrong values in 499 and 500 of 500 input sets from one thread or one warp; stall 0 drains and is right. A crowded launch (68 blocks of 1,024 threads) hides some of these cuts, so single-warp launches are the oracle. All 36 committed kernels, regenerated, return the same bytes as ptxas's originals in one thread, one warp and the crowded launch, over 500 input sets of 10 launches each, although 26 of their instructions stall less than ptxas wrote. A reuse flag left stale on an `IMAD` or `FFMA` whose own result rewrites the register before the next read in that position changed no result in three probes. `ControlWordHardwareSuite` holds four input sets per kernel with the card's outputs, the digests of the regenerated cubins that ran, and the cuts; it checks that the VM computes the card's outputs from both cubins and that the checker reports exactly the cuts the card got wrong. The harness that ran them is not in the repository.

### 3. Hardware validation

- On the sm_89 and gfx1036 cards, run the original and the rewritten kernel and time both, with conformance cases as the correctness check in context.
- A rewrite counts as a gain only when the hardware confirms it. Disagreements between the model and the hardware go back to `static-pipeline.md` as calibration cases.

### 4. Learning, if step 3 justifies it

- Learn a proposal distribution for the search (which move, where), trained on the rewrites search proved and hardware confirmed, rather than a policy that emits code directly.
- The reward stays the proven-correct model gain. Hardware-confirmed results form the held-out set. A target whose model is mostly `Estimate` is excluded from training.

## Non-goals

- Rewriting PTX or SPIR-V. Gains there depend on a compiler the tool does not run.
- Register allocation and instruction scheduling across blocks.
- Shipping a compiler pass. The output is a report and rewritten binaries for study.

## Open decisions

- Window size and the move set per target.
- Whether to stop after step 3 if real gains on compiler output are rare. Recommendation: decide from the step 3 numbers.
